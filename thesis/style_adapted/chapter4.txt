\chapter{UmbraRo: A Mobile Application for Predictive and Prescriptive Football Analytics}
\label{chap:app}

\section{Problem Statement and Specifications}
\label{sec:problem_spec}

Football coaches and technical staff need more than a simple estimate of match outcome. In practice, they require a system capable of presenting match probabilities, identifying the most important tactical and contextual drivers, and translating model outputs into actionable tactical recommendations. Existing football applications are often focused on public score tracking, betting, or fan interaction, rather than on coach-oriented decision support.

UmbraRo was designed to address this gap. The application acts as an AI tactical assistant that combines a machine learning backend with a mobile interface developed in Flutter. Its role is to support match preparation by presenting binary home-win probability, match-specific explanations, and tactical blueprint recommendations generated by the prescriptive optimisation framework of Chapter~\ref{chap:approach}.

From a system-design perspective, UmbraRo must therefore combine predictive accuracy, calibrated probability estimation, interpretable explanations, and realistic tactical prescription inside a single mobile decision-support interface.

\subsection{Functional Requirements}
\label{subsec:functional_req}

The functional requirements of UmbraRo are the following:
\begin{itemize}
    \item \textbf{FR1.} The application shall display the next scheduled match and the corresponding home-win probability.
    \item \textbf{FR2.} The application shall provide a dashboard containing recent and upcoming fixtures.
    \item \textbf{FR3.} The application shall display the baseline win probability and the AI-optimised win probability.
    \item \textbf{FR4.} The application shall present the main positive and negative factors influencing the prediction.
    \item \textbf{FR5.} The application shall display tactical blueprint targets for possession, shots, shots on target, corners, minimum goals scored, and maximum goals conceded.
    \item \textbf{FR6.} The application shall display the recommended starting eleven on a pitch-style visualisation.
    \item \textbf{FR7.} The application shall show fatigue-related indicators based on rest days and schedule density.
\end{itemize}

\subsection{Non-Functional Requirements}
\label{subsec:nonfunctional_req}

The non-functional requirements of UmbraRo are the following:
\begin{itemize}
    \item The application shall provide a clean and minimal interface suitable for fast interpretation during football workflows.
    \item The application shall return analysis results with low waiting time.
    \item The application shall ensure stable communication with the backend service.
    \item The application shall be modular and maintainable for future development.
    \item The application shall preserve a consistent visual identity across all screens.
    \item The application shall be scalable to additional seasons, teams, or competitions.
    \item The application shall provide reliable and interpretable outputs for coaching use.
\end{itemize}

\section{System Architecture}
\label{sec:architecture}

UmbraRo follows a cloud-hosted client-server architecture composed of three layers: a Flutter web/mobile frontend, a Python FastAPI backend, and a set of managed AWS services together with a licensed sports-data feed (Figure~\ref{fig:architecture_umbraro}).

\subsection{Backend Layer}
\label{subsec:backend_arch}

The backend is implemented in Python with the FastAPI framework and exposes a versioned REST API. Its responsibilities are: user authentication delegated to an AWS Cognito user pool with hosted UI, fixture and standings retrieval from the Sportradar licensed sports-data provider, computation of the calibrated home-win probability from the trained CatBoost classifier loaded once at server startup, the constrained Monte Carlo prescriptive optimiser described in Chapter~\ref{chap:approach}, and the player-level starting-XI predictor. Persistent user state (profile, club affiliation, avatar) is stored in an AWS RDS Postgres instance. Passwords are never stored in the application database, since identity is fully delegated to Cognito and the backend only verifies Cognito-issued ID tokens via JWKS. The system is containerised and deployed through a continuous-delivery pipeline on AWS, with the frontend served by AWS Amplify Hosting and the backend container served by AWS App Runner behind an Application Load Balancer that enforces the Cognito identity boundary common to both.

\subsection{Frontend Layer}
\label{subsec:frontend_arch}

The frontend is implemented in Flutter and is organised by feature (authentication, dashboard, match intelligence, lineup pitch, standings, profile) on top of a small shared core module that holds the API client, the authentication state, the localisation layer, and the design tokens (colours, typography, spacing). State management is intentionally lightweight: each feature exposes a small \texttt{ChangeNotifier} surface and the root widget rebuilds when the authenticated user or the active locale changes. Design tokens are centralised so visual consistency is enforced without a heavy theming framework.

\section{Implementation of Key Functionalities}
\label{sec:implementation}

\subsection{Dashboard and Fixture Intelligence}
\label{subsec:f1_impl}

\paragraph{Data flow.}
The dashboard fetches a five-week window of fixtures (two weeks past, the current week, and two weeks ahead) in parallel and caches the result locally, so navigation between weeks requires no additional network round-trip. If the user's club is part of the Romanian Superliga 2024--2025 set, postponed matches whose kickoff is already in the past but whose score is still missing are filtered out by the backend before the response reaches the client.

\paragraph{Fixture card.}
Each fixture is rendered as a tappable card (Figure~\ref{fig:dashboard_card}). For upcoming matches the card displays the calibrated CatBoost home-win probability as a colour-coded percentage (green for high-probability home wins, amber for balanced fixtures, red for unfavourable ones). For completed matches it displays the final score and a result badge. Fixtures involving the authenticated user's club are grouped at the top of the list and highlighted with a left accent border.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.45\textwidth]{figures/dashboard.png}
    \caption{Dashboard fixture card: an upcoming match with win probability on the left and a completed match with score on the right.}
    \label{fig:dashboard_card}
\end{figure}

\paragraph{Week navigation.}
The user navigates between weeks via header controls or a horizontal swipe. Navigation beyond the two-week look-ahead window is disabled both visually and functionally.

\subsection{Match Intelligence and Tactical Blueprint}
\label{subsec:f2_impl}

\paragraph{User value.}
From the coach's perspective, this screen is the one that turns a probability into a plan: it tells the user what the model expects, why, and which tactical levers are most likely to move the outcome. While the Dashboard answers \emph{which} matches are coming and gives a top-level win-probability indicator, the Match Intelligence sheet answers \emph{why} the model produced that probability and \emph{what} the team could realistically change to improve it. It is therefore the most direct on-screen embodiment of the methodological framework presented in Chapter~\ref{chap:approach}.

\paragraph{Data flow.}
Tapping a fixture opens a modal that issues a single request to the backend. The response combines the official event summary (goals, cards, statistics, lineups) with three derived layers: the calibrated CatBoost baseline home-win probability for upcoming fixtures, the optimised probability and blueprint returned by the constrained Monte Carlo optimiser of Chapter~\ref{chap:approach}, and the recommended starting XI. Postponed matches whose kickoff is past but whose score is missing are filtered out at this stage to avoid showing them as upcoming with a probability estimate. The combined payload is cached server-side for twenty-four hours so the modal renders from one network round-trip.

\paragraph{Header and official statistics.}
The modal renders the teams, the final score or scheduled kickoff, and a result badge in its header. Immediately below, a symmetric bar chart compares the home and away values of possession, shots, corners, and fouls, making asymmetries readable at a glance.

\paragraph{Win probability and prescriptive uplift.}
For upcoming matches the sheet adds a probability panel containing two figures: the calibrated CatBoost \emph{baseline} probability of a home win, and the \emph{optimised} probability returned by the constrained Monte Carlo optimiser. The two values are colour-coded against the same green/amber/red thresholds used on the Dashboard, so the coach can compare them visually without re-reading a number. The optimiser respects the domain constraints introduced in Section~\ref{sec:results}: candidate tactical targets must remain inside historically realistic percentile bounds and must preserve basic football logic, so the uplift is always reported alongside a feasible blueprint rather than as an unconstrained numerical maximum.

\paragraph{Drivers and risks.}
A driver panel lists the most influential pre-match features in the current fixture, split into positive and negative contributors. Typical examples include:
\begin{itemize}
    \item Positive: ``Rest advantage: $+5$ days'', ``Elo gap: $+85$'', ``Home win rate last 5: $80\%$''.
    \item Negative: ``Away form: last 3 losses'', ``Shots on target last 5: below league average'', ``Head-to-head: 1 win in last 6''.
\end{itemize}
Drivers are derived from SHAP local feature attributions~\cite{lundberg2017shap,lundberg2020treeshap} (computed with \texttt{shap.TreeExplainer} applied to the raw CatBoost model, see Figure~\ref{fig:shap}) on the same engineered vector that produced the baseline probability, so the explanation layer is consistent with the prediction by construction.

\paragraph{Tactical blueprint targets.}
The blueprint module renders the per-variable targets returned by the optimiser as a compact list of numeric goals: possession (\%), shots, shots on target, corners, minimum goals scored, and maximum goals conceded. Each target is the value at which the model assigned the highest \emph{constrained} home-win probability over all simulated permutations, so the blueprint should be read as a \emph{tactical plan associated with measurable probability uplift} rather than a forecast.

\paragraph{Recommended starting XI.}
Finally, the screen embeds the recommended starting eleven on the FIFA-style pitch panel described in Section~\ref{subsec:lineup_pitch}. The XI is produced by the player-level pipeline described in detail in Section~\ref{sec:xi}. In summary, every available player is scored by a position-aware composite of per-90 KPIs that is shrunk toward the position mean for low-sample players~\cite{brown2008empirical} and z-scored within position before aggregation~\cite{pappalardo2019playerank,mchale2012interfaces}, and the formation slots are filled by a globally optimal Hungarian assignment~\cite{kuhn1955hungarian} over the candidate scores. The result is displayed below the blueprint so that the coach can read the proposed plan and the proposed personnel side by side.

\subsection{Lineup Pitch Visualisation}
\label{subsec:lineup_pitch}

\paragraph{Upcoming matches: recommended XI.}
For upcoming fixtures the lineup panel renders a top-down football pitch with standard markings and positions the recommended starting eleven on a normalised coordinate system. The goalkeeper is fixed near the goal line. Outfield players within each line (defence, midfield, attack) are distributed evenly across the horizontal axis so that the chosen formation reads naturally at a glance.

\paragraph{Completed matches: actual lineups.}
For completed fixtures the same coordinate system displays the real starting elevens returned by the match-detail endpoint. The formation is inferred at runtime by counting starters per coarse position group. The coach can toggle between the home and away teams, and each player chip carries a colour-coded position letter, the jersey number, the surname, and event indicators (goal icon, yellow or red card badge).

\subsection{Multilingual Support}
\label{subsec:l10n}

The application supports Romanian and English. All user-visible strings are resolved through a small localisation layer that holds the per-locale dictionaries (ARB files compiled by the Flutter \texttt{intl} tooling). The selected locale is persisted across app launches and changed from the Profile screen. Switching locale rebuilds the entire widget tree so every label updates simultaneously without navigation. The default locale follows the device language, falling back to English if the device reports a locale outside the supported set.

\section{Mini User Manual}
\label{sec:user_manual}

\subsection{Authentication}

On first launch the application presents the login screen. New users tap \emph{Sign Up} to reach the registration screen, where they provide a full name, email address, and a password of at least eight characters. After successful registration the user is redirected to the dashboard automatically.

\subsection{Dashboard}

The dashboard displays all Romanian Superliga fixtures for the current week. Universitatea Cluj fixtures appear at the top with an accent-coloured left border. The date range shown in the header can be navigated by tapping the left/right chevron arrows or by swiping horizontally across the screen. Pulling down on the list triggers a full data refresh from the server.

Each fixture card shows:
\begin{itemize}
    \item Team names (Universitatea Cluj in bold).
    \item For upcoming matches: the AI-computed win probability in colour-coded text.
    \item For completed matches: the final score and a result badge (V/E/Î, Romanian for \emph{Victorie / Egal / Înfrângere}, i.e.\ W/D/L).
    \item Match date, time, and venue below the team names.
\end{itemize}

Tapping a card opens the Match Intelligence sheet.

\subsection{Match Intelligence Sheet}

\paragraph{Completed matches.}
The sheet header shows the final score. Below it, a bar chart compares possession, shots, corners, and fouls between the two teams. The bottom section shows the actual starting lineups on a pitch diagram. Swipe left or right (or use the team tabs) to switch between the home and away team view. Substitutes are listed below the pitch.

\paragraph{Upcoming matches.}
The sheet shows the baseline win probability alongside the prescriptive-optimised probability. A driver panel lists the top positive factors (e.g.\ ``Rest advantage: $+5$ days'') and negative factors (e.g.\ ``Away form: last 3 losses''). A tactical blueprint section specifies numeric targets for possession, shots, corners, and fatigue. The recommended starting eleven is displayed on the pitch.

\subsection{Profile and Settings}

The profile tab shows the user's avatar, full name, email, and club affiliation. Tapping the avatar allows the user to upload a new profile photo from the device gallery. Language can be changed by tapping \emph{RO} or \emph{EN} in the language selector, and the change takes effect immediately across the entire application. The \emph{Log Out} button signs the user out and returns them to the login screen.
